- 2026-10-20 — 5.2 Block — `8c57d53` — A Block/Unblock row in the same "more" menu (feed card, listing detail, seller profile) suppresses a blocked seller's listings from feed/search symmetrically in both directions, and stops either side messaging the other — enforced in `feed_listings`/`search_listings`'s own WHERE clause, `get_or_create_listing_conversation`'s create-branch, and the `messages` INSERT policy, not just hidden client-side. Existing conversations still open (history survives a block); only starting fresh or sending a new message is refused. Mirrors 5.1's central decision: `blocks`' SELECT policy is owner-scoped to the blocker's own side only, so the blocked party can never confirm who blocked them — which is also why the client-facing `is_blocked_with` wrapper had to be `SECURITY DEFINER` rather than `INVOKER` despite adding no real privilege (an `INVOKER` draft failed live with "permission denied for schema private" the instant the — themselves `INVOKER` — feed/search RPCs tried to call it; verified live by the independent security review, not just read off the migration). Added scope beyond the item's literal wording, flagged in the migration's own header: blocking severs any pre-existing mutual follow, and the `follows` INSERT policy now refuses re-following while blocked, since the severing alone would otherwise be undone by an immediate re-follow.
