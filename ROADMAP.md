# Fynd Roadmap

Source of truth for what gets built next. The `autopilot` skill works through this file top to bottom.

**Rules**
- Work one item at a time, in order. Tick `[x]` only when the item meets its "Done when" and all checks pass.
- Items tagged **[DECISION]** need Roy's input. Stop and ask before building them, then record the answer under the item.
- Never resolve a DESIGN.md **[OPEN]** item yourself. Stop and ask.
- Each milestone ends with a **Checkpoint**: stop, summarize, and wait for Roy to test on a device.
- Out of scope for v1: in-app payments (Stripe Connect), shipping, offers. Deals happen via chat + meet-up.

**Already built:** auth, onboarding, home feed (paging, impressions, favorites), sell flow (drafts, photos, publish), listing detail, public seller profile, chat database (conversations, messages, read RPCs, realtime).

- 2026-10-20 — 5.1 Report — `fd8f523` — A new "more" action rail (feed card, listing detail, seller profile) opens a reason+note report sheet against a listing or a user, reusing the explore tab's chip-wall single-select and the owner-side action-sheet's Sheet+ListRow shape. `reports` is genuinely insert-only — no SELECT policy or grant to any client role at all, stronger than every other table's read shape in this app, matching ROADMAP's own "insert-only for users" wording; `service_role` is the only reader today, and building an admin surface is explicitly out of scope for this item. This branch had silently missed main's scrim-confinement fix (`249b30f`, landed after `autopilot/m4` branched) — caught by code review before commit, since the new action rail touched the exact lines that fix touches; reapplied alongside the new rail rather than left to collide in a future merge. Security review caught three real issues: `listing_id`/`reported_user_id` were `on delete cascade` — the same bug class 4.2's `ai_suggestion_calls` was already fixed for once — which would have let deleting a reported listing/user erase the report itself; changed to `on delete set null`, which in turn required loosening the "exactly one target" CHECK to "at most one" once review-driven testing showed `SET NULL`'s internal UPDATE was tripping the stricter version on every cascade. Also found and fixed the identity sequence not being covered by the table-level revoke (anon/authenticated could read `reports_id_seq` directly to infer report volume) and a `btrim()`-based note-required check that a tab- or no-break-space-only note could slip past.

- 2026-10-20 — 5.2 Block — `8c57d53` — A Block/Unblock row in the same "more" menu (feed card, listing detail, seller profile) suppresses a blocked seller's listings from feed/search symmetrically in both directions, and stops either side messaging the other — enforced in `feed_listings`/`search_listings`'s own WHERE clause, `get_or_create_listing_conversation`'s create-branch, and the `messages` INSERT policy, not just hidden client-side. Existing conversations still open (history survives a block); only starting fresh or sending a new message is refused. Mirrors 5.1's central decision: `blocks`' SELECT policy is owner-scoped to the blocker's own side only, so the blocked party can never confirm who blocked them — which is also why the client-facing `is_blocked_with` wrapper had to be `SECURITY DEFINER` rather than `INVOKER` despite adding no real privilege (an `INVOKER` draft failed live with "permission denied for schema private" the instant the — themselves `INVOKER` — feed/search RPCs tried to call it; verified live by the independent security review, not just read off the migration). Added scope beyond the item's literal wording, flagged in the migration's own header: blocking severs any pre-existing mutual follow, and the `follows` INSERT policy now refuses re-following while blocked, since the severing alone would otherwise be undone by an immediate re-follow. No Critical/High/Medium findings from either review; fixed before commit: "Message seller" could flash visible for an instant on every listing-detail load before the async block check resolved (now also gated on the query's own `isPending`), a missing `errors.test.ts` for `mapBlockError`, a migration comment that literally contradicted the line below it, and one pgTAP coverage gap (anon denied `EXECUTE` on `is_blocked_with`) a review flagged as inconsistent with that suite's own stated discipline.

- 2026-10-20 — 5.3 Mark sold to a buyer — `910c0bb` — Extends 1.6's `mark_listing_sold` with an optional buyer, validated against real conversation history on THIS specific listing, never an arbitrary client-supplied id. Adds a durable `listings.sold_to_user_id` column (nullable — selling outside the app must still work; `set null` not `cascade`, since the buyer's account disappearing later must never delete the seller's own listing) needed by 5.4 "Reviews," the very next item, which needs a durable buyer record to attach a review to. A new `listing_conversation_buyers` RPC feeds the picker — required as a `SECURITY DEFINER` function rather than a direct client query because `conversations`' own column-grant allowlist doesn't include `listing_id` at all (a column-grant gap, not an RLS gap). The picker only appears when there's genuinely more than one person to disambiguate between; marking sold on a listing nobody messaged about keeps the exact pre-5.3 flow. Deliberately lets a since-blocked buyer still be picked, consistent with 5.2's "stop future contact, don't erase the past" — flagged in the migration's own header as a forward-looking question for 5.4's design (should review eligibility ignore block state too, or snapshot at sale time?), not a defect here. No Critical/High/Medium findings from either review; fixed before commit: a loading-state race where tapping "Mark as sold" before the buyer list resolved silently skipped the picker with no indication (now shows a trailing spinner while resolving, without blocking the tap), a duplicated icon constant between two files that would have needed a circular import to share directly (moved into the pure module both already import from), and one missing pgTAP case (a genuine buyer on a listing, not its seller, is rejected by `listing_conversation_buyers` the same as any unrelated party).

- 2026-10-20 — 5.4 Reviews — `ab8b813` — Seller and buyer can each leave a one-time star rating + optional comment after a listing is marked sold to a recorded buyer, surfaced as a "Leave a review" CTA on the conversation screen (gated solely on a new `conversation_detail.can_review` column, no client-side duplicate eligibility logic) and a public reviews list on the seller profile, with average rating and count. `reviews` is insert-only (no update/delete policy at all), unique on `(listing_id, reviewer_id)`, and CASCADE on all three FKs — a deliberate departure from 5.1's "report survives its target" SET NULL, since a review's three identity columns are all NOT NULL by design and a review "about nobody" isn't meaningful the way a moderation report surviving its target is. `submit_review` (SECURITY DEFINER) derives the reviewee server-side from the locked, re-validated listings row — never a client-supplied id — and requires `status = 'sold'` with a recorded buyer; `seller_review_summary` is SECURITY INVOKER, same reasoning as `feed_listings`/`search_listings` (reviews are fully public-read, no privilege boundary to cross). Resolves 5.3's own flagged forward-looking question: review submission is deliberately BLIND to block state — a completed sale is a fact about the past, and a block taken out afterward shouldn't let either party erase or prevent a truthful review of it — verified end to end against the actual reachable code paths (not just the stated intent) with a dedicated pgTAP regression, not merely asserted. `conversation_detail` required a DROP+CREATE to append `can_review` as a new trailing output column — confirmed live that a plain `CREATE OR REPLACE` rejects that shape outright ("cannot change return type of existing function... Use DROP FUNCTION... first"), the same remedy 5.3's arity-changed `mark_listing_sold` needed for an analogous reason. No Critical/High/Medium findings from either review; fixed before commit: a stale, inherited comment on `can_review` claiming a hard-deleted listing must still render its conversation thread via LEFT JOIN, when `conversations.listing_id` is actually `on delete cascade` to `listings` (verified live — that case cannot occur under the current schema; rewritten to state the true behavior and why the LEFT JOIN is kept anyway as cheap future-proofing), an undocumented one-way dependency of `reviews_unique_listing_reviewer` on "sold is terminal" (added a forward-pointing comment at `mark_listing_sold`'s own status-transition guard), a missing `errors.test.ts` for `mapReviewError`, and 4 missing pgTAP cases (`reviews_comment_length`'s bypass-insert path, whitespace-only comment normalization to NULL, `can_review`'s per-viewer rather than per-listing scoping, and a third party's own-perspective false case) — suite grew 44 → 48 assertions, full DB suite now 643/643, mobile 669/669.

- 2026-10-19 — 4.2 Suggest-from-photos Edge Function — `fafecc2` — The first Edge Function in this repo.
